# Philip Butler Workspace Project Brief

## Repository identity
- `occ-eye` is a legacy repository name with no confirmed product meaning.
- Philip does not remember creating or naming OCC-Eye.
- OCC-Eye was never an app idea.
- Do not infer, expand, or assign meanings to OCC-Eye.

## Workspace purpose
Philip Butler Workspace is a neutral Butler and project-office workspace for organizing work, tracking decisions, and maintaining project records.

The workspace exists to:
- organize current and future projects;
- track decisions awaiting Philip;
- maintain backlog, risks, decisions, status, and archive records;
- define a clear process for adding new projects;
- preserve Butler role guidance for planning, delivery, implementation, visual presentation, and verification when those roles are relevant.

## Primary users
- Philip
- Butler agents supporting Philip's planning and project-office work

## Core workflow
1. Capture or clarify a project, task, decision, risk, or status update.
2. Route the work to the smallest relevant Butler role or project-office record.
3. Record next actions, blockers, decisions, risks, and completed or retired work in the project-office files.
4. Ask Philip only for decisions that require Philip's judgment or authority.

## Workspace-management requirements
- Keep `project-office/STATUS.md`, `BACKLOG.md`, `AWAITING_PHILIP.md`, `RISKS.md`, `DECISIONS.md`, and `ARCHIVE.md` current when relevant.
- Replace product assumptions with explicitly labeled unknowns or neutral workspace-management tasks.
- Preserve all Butler role files and the project-office structure.
- Define how new projects are added before turning the workspace into a multi-project system.
- Do not create application code unless Philip later approves a specific application project.

## New-project intake requirements
Before adding a new project, record:
- project working title;
- purpose or outcome;
- owner or responsible Butler;
- current status;
- decisions awaiting Philip;
- risks or dependencies;
- next action;
- where project-specific records should live.

## Technical constraints
- Do not store secrets, tokens, credentials, or private user data in the repository.
- Do not create application code as part of workspace documentation maintenance.
- If future approved work introduces code, use environment variables for external services and add appropriate setup, development, test, and deployment documentation.

- Project documentation uses the working title “Philip Butler Workspace.”
- Project-office records reflect neutral workspace-management tasks and decisions.
